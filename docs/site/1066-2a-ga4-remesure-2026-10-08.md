## 3. Contrôle R4 — les 3 entrées CSP `conditional` sont actives

Le contrôle du runbook n'est pas seulement « les IDs sont dans le HTML » : il exige **0 violation CSP runtime**.
Relevé d'en-tête sur les trois pages (`/terms`, `/privacy`, `/`) :

```
script-src  'self' 'unsafe-inline' 'unsafe-eval' https://cdn.jsdelivr.net https://sibforms.com
            https://cdnjs.cloudflare.com https://ajax.aspnetcdn.com https://www.googletagmanager.com
frame-src   'self' https://www.googletagmanager.com          ← le <noscript> iframe (ns.html)
connect-src 'self' https://api.stripe.com https://region1.google-analytics.com   ← le beacon GA4
```

Identique sur les trois pages. Les trois entrées que la dérivation CSP (`1064-csp-whitelist-derivation.md`)
déclarait **`conditional`** — à n'activer que si les balises GTM migraient — sont **actives**, ce qui est cohérent
avec le fait que les balises sont là.

## 4. Discipline d'instrument

- **Témoin négatif** à chaque passe : `/__temoin_negatif_1066_ga4__` → **404 / 404**. Sans lui, aucun « 200 »
  du tableau §2 n'est interprétable.
- **`GET` uniquement** : sur ce site le `HEAD` rend 404 là où le `GET` rend 200 (constat du 06/10).
- **Cache-buster sur chaque sonde** (cache prod = 1 an).
- **Aucun `catch` n'écrit un verdict** : une exception sort en `error=`, jamais en « 404 » ni « absent ».
  Le rapport du 06/10 documente un instrument qui *fabriquait* de faux 404 ; la branche de secours ne conclut pas.
- ⚠️ **Piège de sous-chaîne, mesuré et écarté.** Mon marqueur `ns.html` remonte **1** occurrence sur la page
  statique — des deux côtés. Vérification faite, c'est un **faux positif** : la chaîne est prise dans
  `…fallacyfiles.org/imptrans.html`. Un marqueur de sous-chaîne n'est pas une balise ; l'occurrence est identique
  des deux côtés, donc sans effet sur la parité, mais elle **aurait** pu se lire comme « la page statique porte
  GTM ».
